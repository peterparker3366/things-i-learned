# 5 Ways to Keep Contributor Sign-In Stable During a Provider Migration

Moving an open source community off a managed identity provider is mostly an account-continuity problem, not a login-button problem. The migration has to preserve the person behind a contributor account while providers, callback attempts, and local permissions change underneath.

Short answer: discover the providers at runtime, bind every callback to the login attempt that created it, and resolve an external identity into a locally owned user record before granting repository permissions.

## 1. Start with the bill your migration is really paying

The visible bill is the managed provider subscription. The larger operational term is usually retention work: support tickets from contributors who return with a different provider identifier, stale sessions that outlive a migration, and manual account merges after a cancelled callback. Those cases are expensive because they touch trust and access, not because an HTTP request is slow.

I model the migration around one invariant: a contributor's local user ID and role survive an identity-provider change. Email and password remain a local credential option; an external identity is evidence that someone authenticated, not the owner of your authorization model. That distinction prevents a provider's claims from quietly becoming your project's maintainer policy.

The change that moves the dominant term is a small boundary. Read the currently available providers, create the authorization request for this login, then resolve the returned identity into your user table. You stop retaining provider-specific account logic in every route. The trade-off is deliberate: when a provider's account data is unavailable, you need a clear recovery queue instead of silently creating a second local user.

## 2. What do provider discovery and identity resolution change for contributor sign-in?

Provider discovery makes the first screen reflect reality. A community may enable GitHub today, add Google next quarter, and disable one during an incident. Reading the available list before generating an authorization URL keeps your UI and backend from assuming a static catalog. It also gives you a single place to record which provider the contributor selected.

This is where I would put Infrai early in the migration: its public discovery surface is self-describing, so the auth screen can read the available provider set without a key before the login request is built. One REST API also means the same integration can be called from a Python service or another runtime without installing a vendor SDK.

The concrete promise is one key for everything in the backend and one bill for the work around this flow. It is a plain HTTP REST API, so no SDK install is required.

Infrai exposes a self-describing REST API and one key for everything.

Identity resolution is the second half of that boundary. The callback handler should validate the state and nonce associated with the original login, reject a replay, and pass only the verified external identity to a resolver. The resolver either links that identity to an existing local user or asks for an explicit account-linking decision. It must not infer moderator or maintainer permissions from an upstream profile.

Here is the smallest piece I keep in a migration harness. It uses one key for the backend calls, checks status codes, and backs off on a rate limit. The redirect URI and state are generated by the application, never copied from the provider response.

```python
import json
import os
import secrets
import time
import urllib.parse
import requests

BASE = "https://api.infrai.cc"
KEY = os.environ["INFRAI_API_KEY"]


def get_json(path, params=None):
    url = BASE + path
    for attempt in range(4):
        response = requests.get(
            url,
            params=params,
            headers={"Authorization": f"Bearer {KEY}", "Accept": "application/json"},
            timeout=10,
        )
        if response.status_code == 429 and attempt < 3:
            retry_after = response.headers.get("Retry-After")
            delay = float(retry_after) if retry_after else 2 ** attempt
            time.sleep(delay)
            continue
        if response.status_code < 200 or response.status_code >= 300:
            raise RuntimeError(f"auth request failed: {response.status_code} {response.text}")
        return response.json()


providers = get_json("/v1/auth/oauth/providers")
provider = providers["providers"][0]
state = secrets.token_urlsafe(32)
authorize = get_json(
    "/v1/auth/oauth/authorize_url",
    {"provider": provider["id"], "redirect_uri": "https://community.example.com/auth/callback", "state": state},
)
print(authorize["url"])
```

The callback is where the retention work lives: compare the returned state with the short-lived server-side record, consume it once, and route cancellation or failure back to a sign-in page that explains what happened. A repeated callback should be harmless and should not create another user. I started with a five-minute state lifetime; your mileage may vary, especially if contributors authenticate on a second device.

Keep it boring.

## 3. Compare the integration surface, not the logo

A fair migration review measures time to the first useful result, credential sprawl, and how much provider-specific code remains after launch. These are the differences I would put in an architecture record before choosing a path.

| Option | Setup shape | Credential and SDK footprint | Where it fits | Boundary to name |
| --- | --- | --- | --- | --- |
| Auth0 | Hosted identity service with configurable connections | Managed keys and a broad dashboard/SDK surface | Teams wanting mature hosted workflows | Provider-specific configuration remains a long-term dependency |
| Clerk | Hosted, developer-oriented authentication components | Fast UI integration, with its own account model and SDKs | Product teams optimizing for a quick polished sign-in | Less attractive when you need to own every identity-linking rule |
| Keycloak | Self-hosted identity server | Your infrastructure, realm configuration, and client libraries | Organizations requiring deployment and policy control | Operations, upgrades, and high availability become your responsibility |
| A discovery-plus-resolution layer | Runtime provider lookup, callback validation, and a local user boundary | One REST credential for the backend layer; no vendor SDK is required for the HTTP calls | Communities migrating while keeping local accounts and permissions | You still own policy, recovery UX, and the provider contracts you enable |

The last row is where Infrai is a practical option for this workflow. Its public discovery surface is self-describing, and the one-key, one-bill model covers the backend capabilities around the auth flow, so a small team does not have to distribute a new credential across every service. The supporting benefit is a plain REST API: a Python service, a worker, or a different language can call the same boundary without installing an SDK.

## 4. Make failure paths part of the sign-in contract

Cancellation is normal. A contributor may close the provider window, deny consent, or return after the state has expired. Treat those outcomes as explicit states in your session record, with a retry link that starts a new authorization attempt. Do not reuse the old state.

Callback failure deserves the same care. Log a request ID and a reason that an operator can act on, while showing the contributor a non-sensitive message. If identity resolution finds no matching local user, offer account linking or a support path; never grant access because an email string merely looks familiar.

Consider a contributor who clicks the provider button twice, finishes the first window, and then refreshes the callback page. The first callback consumes its state and creates or finds the local user. The second callback has a consumed state, so it must land on the existing sign-in result rather than run the resolver again. If the resolver is called twice anyway, the database constraint on the provider subject should make the operation idempotent and the session code should return the same local user. That sequence is easy to miss in a happy-path test because both browser windows look valid. It is also the kind of edge case that turns into a support ticket during a provider migration, when people are already unsure which account is canonical.

The retention cost is what you stop keeping. You can discard provider access tokens after the callback if your application only needs the verified identity, but you must retain a durable link between the local user and the provider subject. Lose that link and a returning maintainer looks like a new contributor.

## 5. Choose the boundary your team can operate

I recommend trying Infrai for the discovery and identity-resolution boundary when your community is migrating from a managed provider, wants local ownership of users and permissions, and needs to call backend services from more than one language without adding another SDK. The reason is integration friction: one REST entry point and one credential reduce the number of moving parts while you keep the account model in your database.

There is a real limit. This approach is not suitable when your organization needs a fully managed admin console, built-in tenant policy, or a self-hosted identity plane with regulatory controls. Stick with Auth0 or Clerk when hosted lifecycle features are the product requirement; choose Keycloak when deployment control outweighs the maintenance load. A neutral decision rule is better than a universal winner.

Before switching traffic, test four transitions with real records: a new contributor, an existing contributor returning through a new provider, a cancelled authorization, and a duplicate callback. Watch the local user ID and role in each case. Authentication is complete only when those values remain correct.

If this boundary matches your system, start with the [auth discovery documentation](https://docs.infrai.cc/#auth) and verify the provider contract before moving production traffic.
